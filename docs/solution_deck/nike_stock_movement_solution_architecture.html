  • One Databricks job (nike_stock_movement_pipeline) rebuilds every recommendation daily at 10:30 GST and on demand from the app: store-to-store consolidation and DC-to-store replenishment, joined by a receiver full-size guard.

Architecture choices

  • Serverless everywhere: the job, the warehouse and the apps start on demand; nothing idles outside 07:00-19:00 except the daily job.
  • One schema for engine, forecast, launches, agents and decisions keeps lineage and grants simple; history tables carry the run_id.
  • Notebooks as steps: each step is one notebook with a frozen run_config, so any step can be rerun or debugged in isolation.
  • Delta replace + append: step outputs are replaced each run (cheap, always current); *_history tables append per run (audit, run picker, Genie history).
  • No secrets in code: user OAuth for people, app service principals for app-to-job, CLI SSO for builders.
Unity Catalog system tables (system.lakeflow, system.access) are not granted to the project user, so run history for the agents comes from the Jobs API instead.

Forecast, allocation and new launches

Forecast and allocation (notebook 20)

Demand-led allocation for styles with history, all Nike stores aggregated by country

Method

  • Weekly demand per country x style, 8-week horizon; history censored for stock-outs (sqrt gross-up below 70% availability) and events 2024-27.
  • Tournament per series: MA4, MA12, SES, Croston SBA, TSB; a seasonal variant only wins if it beats flat by more than 1 point of error.
  • Uncertainty: negative binomial with alpha learned per volume band; P80 = 80% service level; slow-style calibration fades out above 0.25-0.5 a week.
  • Store split by the store's share of division x gender sales; size split by country x division x AH2 x gender curve (GCC curve when thin).
  • Allocation: units covering 80% of 14-day outcomes, at least 1 per key size, rationed from the primary DC then the UAE hub by grade.

Forecast for styles with no sales (Spring 2027)

  • 5,851 styles, 403K units in the first 13 weeks; launch week assumed from last spring until buyer dates arrive.
  • Look-alikes: 10 closest past launches (category, sport, silhouette, life cycle, colour, price) blended 50/50 with earlier colourways of the same model.

  • Back-test on Spring 2026: country ±11%, division x gender ±15%, style 82% error (45% within 2x), P80 covers 80%.

The apps

When a planner presses ▶ Run stock movement

Seven steps from click to reviewed results
  1. Inputs checked in the app. Protect cover must be below target cover; the size definition must validate; the button is disabled while a run is in progress.
  2. Uploaded files saved first, as the planner, into the cfg_ tables (size definition, BU matrix, store list, kids bands).
  3. The app mints a run ID (UTC time + 6 hex) and calls jobs/run-now on job 553755400746008 with COUNTRY, CATEGORY, six cover settings, RUN_ID and TRIGGERED_BY = the planner's e-mail. The app's service principal has Can manage run; the job runs as its owner.
  4. A status card follows the run every 4 seconds: "Running · step N of 13", with a link to the run. Reopening the app picks the run back up.
  5. The 13 steps run (about 8 minutes); queued if another run is going (max 1 concurrent).
  6. Results load by run ID from the *_history tables, so the planner sees exactly their run; the run picker lists every run with who ran it and its scope.
  7. On failure the card names the failed task; earlier steps may have refreshed the latest tables, but nothing is archived, so the run never appears in the picker.

Skill 1: run-nike-stock-movement

A confirmed, parameterised run, never a surprise run

What it does

  • Runs the engine with default or changed settings, from a conversation.
  • Always asks first: shows the ten settings with defaults, asks what to change, validates, shows the final table, asks 'Run with these settings?'.
  • Validates like step 00: whole numbers 1-365, protect cover < target cover, ISO country codes, the 20 business categories, dates not in the future.
  • Warns: about 8 minutes, one run at a time, a scoped run replaces the app's latest view until the next full run.
  • Starts with POST /api/2.2/jobs/run-now, follows runs/get every 30 s, summarises from the history tables.
  • No jobs tool or permission → gives the job link and the settings to run by hand.

Flow

  1. User: "run the stock movement"
  2. Skill shows defaults, asks what to change
  3. User changes (e.g. COUNTRY = AE, TARGET 21)
  4. Skill validates, shows final table, asks to confirm
  5. run-now with RUN_ID + TRIGGERED_BY
  6. Progress by step, then results vs last scheduled run
